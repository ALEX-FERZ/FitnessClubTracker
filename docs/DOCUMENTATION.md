## 1. Общая схема работы

Программа построена по **многослойной архитектуре**. Каждый слой обращается только
к слою ниже и ничего не знает о слоях выше:

```
┌──────────────────────────────┐
│  ui/          Интерфейс      │  меню, ввод с клавиатуры, вывод на экран
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  services/    Бизнес-логика  │  проверки и правила (есть ли места, абонемент…)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  repositories/ Доступ к данным│  все SQL-запросы (CRUD)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  database/    SQLite         │  подключение к файлу database.db
└──────────────────────────────┘

models/     — структуры данных, которыми обмениваются все слои
constants/  — общие константы (роли, статусы, пути к файлам)
export/     — выгрузка данных в JSON, CSV, XML, YAML (ЛР5)
```

**Пример — клиент записывается на занятие:**

1. `ui/Menu.cpp` — клиент выбирает пункт «2. Записаться на занятие» и вводит номер занятия.
2. `services/BookingService.cpp` — функция `book()` проверяет: занятие существует, клиент
   ещё не записан, есть свободные места, есть абонемент на дату занятия с остатком посещений.
3. `repositories/BookingRepository.cpp` — функция `create()` выполняет
   `INSERT INTO Booking ...`, а `SubscriptionRepository::updateVisits()` списывает одно посещение.
4. `database/Database.cpp` — через подключение `db` запрос выполняется в файле `database.db`.
5. Если какая-то проверка не прошла, сервис бросает `std::runtime_error`, меню ловит её в
   `try/catch` и печатает «Ошибка: …». Программа при этом не падает.

### База данных (`database/database.sql`)

| Таблица | Поля | Назначение |
|---|---|---|
| `User` | `UserID` (PK), `login`, `passwordHash`, `role`, `fullName`, `phone` | пользователи: `role = 0` — клиент, `role = 1` — администратор |
| `Trainer` | `TrainerID` (PK), `fullName`, `phone` | тренеры; в систему не входят, их добавляет администратор |
| `Lesson` | `LessonID` (PK), `TrainerID` (FK), `title`, `startTime`, `maxPlaces` | занятия в расписании |
| `Subscription` | `SubscriptionID` (PK), `ClientID` (FK), `type`, `startDate`, `endDate`, `visitsLeft` | абонементы клиентов |
| `Booking` | `BookingID` (PK), `ClientID` (FK), `LessonID` (FK), `createdAt`, `status` | записи на занятия: `status = 1` — активна, `0` — отменена |

**Связи:**

- `Trainer` 1 : N `Lesson` — один тренер ведёт много занятий;
- `User` 1 : N `Subscription` — у клиента может быть несколько абонементов;
- `User` 1 : N `Booking` и `Lesson` 1 : N `Booking` — клиенты и занятия связаны
  «многие ко многим» через таблицу `Booking`.

Если файла `database.db` нет, программа при запуске сама создаёт его из `database.sql`.

## 4. Лабораторная работа №4 — слои приложения

**Задание ЛР4:** модели данных для всех таблиц, репозитории с операциями CRUD, слой сервисов
с бизнес-логикой, консольный интерфейс, авторизация и регистрация с разграничением ролей.

### 4.1. Точка входа — `src/main.cpp`

1. `setupConsole()` — включает UTF-8 в консоли, чтобы работали русские буквы.
2. `openDatabase(DB_PATH, SQL_PATH)` — открывает базу (или создаёт её из `database.sql`).
3. `mainMenu()` — показывает главное меню. Программа работает, пока пользователь не выберет «0».
4. `closeDatabase()` — закрывает подключение к базе.

### 4.2. Константы — `src/constants/`

| Файл | Что внутри |
|---|---|
| `Constants.h` | **объявления** констант через `extern const` — подключается во всех файлах, где они нужны |
| `Constants.cpp` | **значения** констант — заданы один раз |

| Константа | Значение | Где используется |
|---|---|---|
| `ROLE_CLIENT`, `ROLE_ADMIN` | `0`, `1` | роли пользователей (поле `User.role`) |
| `BOOKING_CANCELLED`, `BOOKING_ACTIVE` | `0`, `1` | статус записи (поле `Booking.status`) |
| `DB_PATH`, `SQL_PATH` | `database/database.db`, `database/database.sql` | пути к базе |
| `OUT_DIR` | `out` | папка для экспорта |
| `MIN_PASSWORD_LENGTH` | `4` | минимальная длина пароля |
| `PASSWORD_PREFIX` | `hash_` | учебный «хэш» пароля |

Зачем так: если нужно поменять значение (например, длину пароля), достаточно исправить
одну строку в `Constants.cpp`, а не искать числа по всему проекту.

### 4.3. Подключение к базе — `src/database/`

| Функция | Что делает |
|---|---|
| `openDatabase(dbPath, sqlPath)` | открывает файл базы через `sqlite3_open`, включает проверку внешних ключей (`PRAGMA foreign_keys = ON`). Если файла не было — выполняет весь `database.sql` |
| `closeDatabase()` | закрывает подключение (`sqlite3_close`) |
| `columnText(stmt, col)` | достаёт текст из столбца результата запроса; если там `NULL` — возвращает пустую строку |

Переменная `db` (`sqlite3*`) — единственное подключение к базе на всю программу.
Её используют все репозитории.

### 4.4. Модели данных — `src/models/`

Модель — это структура (`struct`), которая соответствует одной таблице базы. Благодаря
моделям в коде пишется `lesson.title`, а не `row[2]`.

| Файл | Таблица | Поля |
|---|---|---|
| `User.h` | `User` | `id`, `login`, `passwordHash`, `role`, `fullName`, `phone` |
| `Trainer.h` | `Trainer` | `id`, `fullName`, `phone` |
| `Lesson.h` | `Lesson` | `id`, `trainerId`, `title`, `startsAt`, `capacity` + **дополнительные** `trainerName`, `booked` |
| `Subscription.h` | `Subscription` | `id`, `clientId`, `type`, `startDate`, `endDate`, `visitsLeft` |
| `Booking.h` | `Booking` | `id`, `clientId`, `lessonId`, `createdAt`, `status` + **дополнительные** `clientName`, `lessonTitle`, `lessonTime` |

**Дополнительные поля** в таблицах не хранятся. Они заполняются при JOIN-запросе, чтобы в
меню показывать имя тренера вместо его номера, количество записавшихся и т. п.

### 4.5. Репозитории (доступ к данным) — `src/repositories/`

Репозиторий — это набор функций для работы с **одной** таблицей. **Все SQL-запросы проекта
находятся только здесь.**

Каждая функция работает по одной схеме:

```cpp
sqlite3_stmt* stmt;
sqlite3_prepare_v2(db, "SELECT ... WHERE UserID = ?", -1, &stmt, nullptr); // 1. подготовить запрос
sqlite3_bind_int(stmt, 1, id);                                             // 2. подставить значение вместо ?
while (sqlite3_step(stmt) == SQLITE_ROW) { ... }                           // 3. выполнить, прочитать строки
sqlite3_finalize(stmt);                                                    // 4. освободить память
```

Знак `?` и функции `sqlite3_bind_*` защищают от **SQL-инъекций**: введённый пользователем
текст никогда не становится частью SQL-команды.

| Файл | Функции | CRUD |
|---|---|---|
| `UserRepository` | `create`, `getById`, `getByLogin`, `getByRole`, `update`, `remove` | C, R, U, D |
| `TrainerRepository` | `create`, `getById`, `getAll` | C, R |
| `LessonRepository` | `create`, `getById`, `getAll`, `update`, `remove` | C, R, U, D |
| `SubscriptionRepository` | `create`, `getByClient`, `updateVisits`, `remove` | C, R, U, D |
| `BookingRepository` | `create`, `getByClient`, `getByLesson` | C, R |

Особенности:

- `LessonRepository` одним запросом получает занятие, ФИО тренера (`JOIN Trainer`) и число
  активных записей (`SELECT COUNT(*) FROM Booking ...`).
- `LessonRepository::remove` сначала удаляет записи на занятие из `Booking`, а потом само
  занятие — иначе не даст внешний ключ.
- `BookingRepository` подставляет ФИО клиента и название занятия через `JOIN User` и `JOIN Lesson`.

### 4.6. Сервисы (бизнес-логика) — `src/services/`

Сервисы содержат **правила** системы. SQL здесь нет — сервисы вызывают репозитории.
Если правило нарушено, сервис бросает `std::runtime_error` с понятным текстом.

#### `AuthService` — вход и регистрация

| Функция | Что делает |
|---|---|
| `hashPassword(password)` | возвращает `PASSWORD_PREFIX + пароль` (учебный «хэш», например `hash_1`) |
| `login(login, password)` | ищет пользователя по логину и сравнивает хэш пароля |
| `registerUser(login, password, role, fullName, phone)` | регистрирует клиента или администратора |

Проверки при регистрации: роль — только клиент или администратор, логин не пустой,
пароль не короче `MIN_PASSWORD_LENGTH`, ФИО не пустое, логин ещё не занят.

#### `LessonService` — расписание и тренеры

| Функция | Что делает и что проверяет |
|---|---|
| `getSchedule()` | список всех занятий |
| `getTrainers()`, `addTrainer(fullName, phone)` | база тренеров и добавление тренера (ФИО не пустое) |
| `getById(lessonId)` | занятие по номеру; если нет — ошибка «Занятие не найдено» |
| `addLesson(trainerId, title, startsAt, capacity)` | тренер существует; название не пустое; дата в формате `ГГГГ-ММ-ДД ЧЧ:ММ`; мест больше 0; **у тренера нет другого занятия в это же время** |
| `editLesson(lessonId, title, startsAt, capacity)` | те же проверки данных + мест не меньше, чем уже записано |
| `deleteLesson(lessonId)` | занятие существует, затем удаляет его вместе с записями |
| `getBookings(lessonId)` | кто записан на занятие |

#### `BookingService` — записи и абонементы

| Функция | Что делает и что проверяет |
|---|---|
| `book(clientId, lessonId)` | занятие существует → клиент ещё не записан → есть свободные места → есть абонемент на дату занятия → на абонементе остались посещения. Затем создаёт запись и списывает одно посещение |
| `getClientBookings(clientId)` | записи клиента |
| `getSubscriptions(clientId)` | абонементы клиента |
| `addSubscription(clientId, type, startDate, endDate, visits)` | клиент существует и это именно клиент; тип не пустой; даты в формате `ГГГГ-ММ-ДД`; дата окончания не раньше начала; посещений больше 0 |

### 4.7. Интерфейс — `src/ui/`

### 4.8. Авторизация и роли

- Роль хранится в поле `User.role`: `0` — клиент, `1` — администратор.
- При регистрации пользователь выбирает роль. Администраторов может быть несколько.
- Пароль в базе хранится как `hash_<пароль>`. Это учебная заглушка вместо настоящего хэша:
  у пользователя `ivanov` в базе `hash_1`, значит его пароль — `1`.
- Тренеры не являются пользователями и не входят в систему.

## 5. Лабораторная работа №5 — форматы данных

**Задание ЛР5:** выбрать таблицу, связанную с другой таблицей, извлечь записи SQL-запросом и
автоматически создать в папке `out` файлы `data.json`, `data.csv`, `data.xml`, `data.yaml`.
Связанные данные вложить в структуру (в CSV — объединить в строке). Папка `out` должна
создаваться автоматически, код должен быть универсальным.

### 5.1. Где находится

| Файл | Что внутри |
|---|---|
| `src/export/Exporter.h` | объявления функций экспорта |
| `src/export/Exporter.cpp` | загрузка данных из базы и четыре функции сериализации |
| `out/data.*` | готовые файлы |

Запуск экспорта: войти администратором → пункт **«8. Экспорт расписания»**.

### 5.2. Какие данные выгружаются

Таблица **`Lesson`** (занятия) вместе со связанными данными:

- **тренер** из таблицы `Trainer` (связь 1:N) — вкладывается как объект `trainer`;
- **записавшиеся клиенты** из `User` через `Booking` (связь M:N) — вкладываются как список `clients`.

SQL-запрос (функция `exportLessons`):

```sql
SELECT l.LessonID AS id, l.title AS title, l.startTime AS startTime, l.maxPlaces AS maxPlaces,
       u.TrainerID AS "trainer.id", u.fullName AS "trainer.fullName", u.phone AS "trainer.phone",
       (SELECT group_concat(c.fullName, ';')
          FROM Booking b JOIN User c ON c.UserID = b.ClientID
         WHERE b.LessonID = l.LessonID AND b.status = 1) AS "clients[]"
FROM Lesson l JOIN Trainer u ON u.TrainerID = l.TrainerID
ORDER BY l.startTime
```

### 5.3. Как работает (почему код универсальный)

Структура файла задаётся **названиями столбцов** в SQL-запросе:

| Название столбца | Что получится |
|---|---|
| `title` | обычное поле `title` |
| `trainer.fullName` | поле `fullName` внутри вложенного объекта `trainer` |
| `clients[]` | список `clients`; элементы приходят одной строкой через `;` (её собирает `group_concat`) |

Код экспорта ничего не знает о таблицах `Lesson` или `Trainer`. Чтобы выгрузить другую
таблицу, достаточно вызвать `exportQuery()` с другим SQL-запросом.

**Порядок работы `exportQuery(sql, tableName, outDir)`:**

1. `std::filesystem::create_directories(outDir)` — создаёт папку `out`, если её нет.
2. `loadRows(sql)` — выполняет запрос. Для каждой строки результата смотрит название столбца
   и тип значения (`sqlite3_column_type`): число, текст или `NULL`. Столбцы с точкой
   собираются во вложенный объект, столбцы с `[]` превращаются в список.
3. Те же данные записываются четырьмя функциями: `toJson`, `toCsv`, `toXml`, `toYaml`.
4. `save()` — записывает каждый файл и печатает «Создан файл out/…».

### 5.4. Особенности каждого формата

| Формат | Функция | Вложенность | Особенности |
|---|---|---|---|
| JSON | `toJson` | `trainer` — объект `{ }`, `clients` — массив `[ ]` | числа без кавычек, текст в кавычках, пустое значение — `null` |
| CSV | `toCsv` | нет — тренер раскладывается в столбцы `trainer.id`, `trainer.fullName`, `trainer.phone`, клиенты пишутся через `;` | первая строка — заголовок; в начале файла BOM, чтобы Excel правильно показал русские буквы; значения с `,` `;` `"` берутся в кавычки |
| XML | `toXml` | `<trainer>…</trainer>`, `<clients><client>…</client></clients>` | корневой тег `<lessons>`, каждая запись — `<lesson>`; символы `&` `<` `>` экранируются |
| YAML | `toYaml` | вложенность отступами, список через `- ` | текст в кавычках, пустой список — `[]` |

## 6. Сборка и запуск

Нужен компилятор **g++** с поддержкой C++17 (MSYS2 UCRT64 или MinGW-w64).
Все команды выполняются в терминале из корня проекта.

```bash
.\build.bat
.\build\fitness_club.exe
```

Что делает `build.bat`:

1. Создаёт папку `build`.
2. Один раз компилирует библиотеку SQLite: `gcc -c third_party\sqlite\sqlite3.c -o build\sqlite3.o`.
3. Компилирует все `.cpp` из `src` и собирает их вместе с SQLite в `build\fitness_club.exe`:
   `g++ -std=c++17 -Isrc -Ithird_party\sqlite ... -static -o build\fitness_club.exe`.

Если `gcc` не найден, сначала выполните:

```bash
$env:PATH = "C:\msys64\ucrt64\bin;" + $env:PATH
```

Вернуть исходные тестовые данные:

```bash
git checkout -- database/database.db
```
